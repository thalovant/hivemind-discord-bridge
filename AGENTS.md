# AGENTS.md — `hivemind-discord-bridge`

Guidance for AI coding agents (and humans) working in this repository. Read it
fully before making changes. It encodes conventions that are not obvious from the
code and that, if ignored, produce work that will be rejected.

## Repo

Bridges a Discord bot to a HiveMind node: a HiveMind bridge is a satellite
whose input and output are a chat platform instead of a microphone. Inbound
Discord text messages (channels the bot can read, plus DMs) become
`recognizer_loop:utterance` bus messages; the hub's `speak` replies are
posted back into the originating channel or DM. Part of the
[HiveMind](https://github.com/JarbasHiveMind) ecosystem — a protocol for
connecting satellite devices to a hub running
[OpenVoiceOS](https://github.com/OpenVoiceOS). The hub is
[HiveMind-core](https://github.com/JarbasHiveMind/HiveMind-core); the client
library is
[hivemind-bus-client](https://github.com/JarbasHiveMind/hivemind-bus-client).
Sibling bridges with the same shape: `hivemind-telegram-bridge` and the other
chat-platform bridges under the org — check them for prior art before
inventing a new pattern here. Text-only; voice channels are documented in the
README as a deliberately unimplemented future direction, not a gap to fill
casually.

## Layout / build / test

- Package module: `hivemind_discord_bridge/`. Tests live in `tests/` (check
  before adding — do not create a second test directory).
- Set up a throwaway environment inside your clone; never touch a shared venv:
  `python3 -m venv .venv && VIRTUAL_ENV=$PWD/.venv uv pip install -e ".[test]" --prerelease=allow`
- Run the suite in the foreground: `python3 -m pytest tests/ -q`. It mocks
  both `discord.Client` and `HiveMessageBusClient`, so it runs without a live
  bot token or hub — that also means it cannot catch a real handshake hang or
  a real Discord gateway break; treat it as a shape/wiring check, not a
  live-behaviour guarantee.
- `uv`, never `pip`. If latest prereleases fail to install or resolve, that is
  a bug to FIX at the source, not to work around with a pin downgrade.

## Repo-specific rules

- **Composition, not inheritance.** `HiveMindDiscordBridge.__init__` builds
  (or accepts an injected) `HiveMessageBusClient`, but `HiveMessageBusClient`
  never opens a connection in its own `__init__`. The actual connection
  happens once, in `connect_hivemind()`, called from `start()`. Never add a
  second call to `connect()`, and never call `run_forever()` in addition to
  it — `connect()` already starts and owns the reconnect worker thread for
  as long as the process runs.
- **`connect()` must bound `handshake_max_retries`.** The
  `hivemind-bus-client` floor is `>=1.0.13a1`; that client's own default for
  `handshake_max_retries` is `None`, meaning retry forever, which hangs a
  bridge against a stalled or unreachable hub (down, wrong password).
  `connect_hivemind()` passes an explicit finite `handshake_max_retries`
  (`DEFAULT_HANDSHAKE_MAX_RETRIES`, a constructor parameter); any change
  to it must keep that bound.
- **The hub owns ACL, not this bridge.** A freshly registered HiveMind client
  is denied every message type until an admin runs `hivemind-core allow-msg
  recognizer_loop:utterance <client_id>` (and usually `speak`). This bridge
  has no way to grant itself permissions and must not try to work around a
  denial locally — a silently dropped message on the hub side is the hub
  doing its job, not a bug here. The hub says so with `hive.policy.denied`
  (code `acl_disallowed_type`); the bridge logs the grant hint then, once,
  and never at start (a managed hub grants the type itself).
  `--allowed-channel` is a separate,
  bridge-side filter over which Discord channels may originate traffic (DMs
  follow `--dm-policy`, refused by default when channels are listed); it is
  not a substitute for hub-side
  message-type ACLs.
- **Rejected credentials must fail fast.** With `handshake_max_retries`
  bounded (see above), a wrong access key/password turns into a clean
  failure instead of a bridge that spins forever looking connected. A
  Discord token Discord refuses (`LoginFailure`, gateway close 4004) ends
  the bridge with `token_rejected` in `/dev/termination-log` and exit
  status 3; keep that path free of retries too. Do not
  add retry/backoff logic on top of `connect()` that defeats this.
- **Forward upstream responses verbatim.** `handle_speak()` forwards
  `message.data["utterance"]` to Discord unmodified; do not reformat,
  truncate, or add bridge-specific decoration to hub-authored text. A reply
  longer than one Discord message is split (`split.py`) in order, never
  shortened: a whitespace run that would make a blank message is joined
  to the text next to it (`_place_whitespace`), only whitespace no message
  could carry beside visible text is left out; and it is sent with
  `AllowedMentions.none()`
  so it pings no one. The bridge-authored lines are the ones in
  `lines.py`, said only when the hub sent nothing to relay: no skill
  matched (`complete_intent_failure`), or no answer came (reply timeout,
  hub unreachable, refusal). Keep them short and add a language to every
  line at once (the Telegram bridge has the same table).
- **Thread safety.** `speak()` runs on the HiveMind bus's own thread, never
  on the asyncio loop `discord.py`'s `Client` uses. Any new HiveMind →
  Discord path must go through `asyncio.run_coroutine_threadsafe` (or
  `_on_loop`) the same way (see `speak()` / `_deliver()`) — a direct
  `await` from the bus thread will raise or silently no-op depending on
  timing.
- **Neither side waits for the other.** The bus thread never waits for a
  Discord call (no `future.result()`): it also delivers every other hub
  message and the client's keepalive. The Discord loop never calls
  `client.emit()`: hub sends go through the single `_hub_sender` thread, in
  order (the client's encrypted transport is not written from two threads,
  and a blocked loop misses gateway heartbeats); `stop()` shuts it down
  with its queue cancelled. Waiting state (`_pending`, one `_Question` per
  question, matched to replies by the `bridge_question` number the hub
  echoes; typing; the per-channel send locks, the channel cache) lives on the loop
  only. `tests/test_latency.py` measures both directions; keep it green.
- **Never log what people wrote.** `emit()` errors carry the serialized
  message: log the kind of error only.
